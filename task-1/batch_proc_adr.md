1. Родительский артефакт - нет

## Контекст
Выбор решения для пакетной обработки данных

## Рассмотренные варианты

### Вариант №1 Apache Airflow
Ключевой принцип работы Apache Airflow — Workflow as Code. Это подход, при котором весь процесс обработки данных описывается с помощью кода, а не через интерфейс или YAML. Пайплайн описывается в Python-коде, где используется DAG (Directed Acyclic Graph) — направленный ациклический граф. В нём узлы представляют отдельные задачи, а стрелки указывают на то, в какой последовательности эти задачи должны выполняться и от каких шагов они зависят. 

### Вариант №2 Spring Batch
Spring Batch — это фреймворк для пакетной обработки данных. Он помогает решать типовые задачи ETL-класса (чтение, трансформация и запись больших объёмов данных), обеспечивая масштабируемость, отказоустойчивость и удобный контроль выполнения.


### Вариант №3 Spring Cloud Data Flow (SCDF)
SCDF это оркестратор для запуска и управления data-пайплайнами, который работает как «надстройка» над Spring Batch (для пакетных задач) и Spring Cloud Stream (для потоковых задач), которая объединяет отдельные микросервисы и процессы в единую систему.


## Критерии оценки
-  возможность гибко формировать пайплайн (возможность ветвления, условных операторов и event-triggers);
-  интегрировать его с внешними API, BigQuery, Redshift, Kafka и Spark;
-  встроенный мониторинг и оповещения;
-  объём обрабатываемых данных за один запуск пайплайна около 1 млн;
-  развертывание решения в облачной среде;

## Сравнение альтернатив

### Возможность гибко формировать пайплайн, ветвления и event-triggers
#### Вариант №1 Apache Airflow
Пайплайны описываются как DAG  на чистом Python. Это дает максимальную гибкость: динамическое создание задач, сложные ветвления и зависимости. Есть так называемые сенсоры(Sensors) типа ожидание файла, HTTP-ответа или сообщения. Начиная с версии 3.0, появилась полноценная поддержка Event-driven scheduling, позволяющая запускать DAG при получении сигналов.

#### Вариант №2 Spring Batch
Ориентированы на фиксированную структуру (Reader-Processor-Writer).
Не имеет встроенного механизма ожидания событий. Это библиотека для выполнения задач по расписанию или ручному запуску.

#### Вариант №3 SCDF
Имеется вариант оркестрации зависимостей между задачами(job'ами).
Но, кажется, описывать сложную топологию графа в них менее интуитивно чем в Airflow.
Интеграция с event-driven запуском, подходит для событийных моделей. Построен на архитектуре микросервисов, которые могут запускаться по HTTP-запросу, событию в Kafka/RabbitMQ

### Интегрировать его с внешними API, BigQuery, Redshift, Kafka и Spark.
#### Вариант №1 Apache Airflow
У него есть готовые провайдеры (Operator) для BigQuery, Redshift, Kafka и Spark.

#### Вариант №2 Spring Batch
Интеграции с внешними сервисами и API может потребовать написания Java кода.

#### Вариант №3 SCDF
Интеграции с внешними сервисами и API может потребовать написания Java кода.

### Встроенный мониторинг и оповещения

#### Вариант №1 Apache Airflow
Имеется веб-интерфейс, где видно каждый шаг, логи каждой задачи и время выполнения. Можно легко 
настраивать оповщения при сбоях в Slack/Telegram/Email.

#### Вариант №2 Spring Batch
Особо развитого UI нету, для мониторинга используют логи и базовой метаинформации в JobRepository.
UI соотв. сервисов для запуска задач типа Quartz и т.п.

#### Вариант №3 SCDF
Есть интеграция с Prometheus/Grafana, есть UI для управления задачами.

### Объём обрабатываемых данных за один запуск пайплайна около 1 млн

#### Вариант №1 Apache Airflow
Для малого (несколько тысяч строк) достаточно локального выполнения через PythonOperator. Для среднего объёма (миллионы строк) нужны инструменты вроде Spark или Dask, которые Airflow может запускать через SparkSubmitOperator. Для очень больших объёмов (терабайты) Airflow сам данные не обрабатывает, но отлично оркестрирует системы, которые это умеют делать, такие как Spark, Flink, BigQuery или Snowflake

#### Вариант №2 Spring Batch
Скорее всего объем в 1 млн будет несколько затруднительно обработать в рамках одной машины.

#### Вариант №3 SCDF
Вполне обычный объем для данной технологии.

### Развертывание решения в облачной среде

#### Вариант №1 Apache Airflow
«Cloud-native» решение, у всех крупных облачных вендоров есть свои Airflow решения.

#### Вариант №2 Spring Batch
Можно запускать в облаке по расписанию. Обычно для этого используется Kubernetes CronJob или  оркестраторы вроде Airflow и Spring Cloud Data Flow в более сложных инфраструктурах, где нужно оркестрировать множество job'ов.

#### Вариант №3 SCDF
Ориентирован на запуск в Kubernetes. Он динамически создает поды в K8s для каждой задачи (Task) или стрима. Управляемых (PaaS) версий от облачных провайдеров практически нет.



## Принятое решение
Для выбранных критериев, выбор стоит, по сути, между Apache Airflow и SCDF. В целом нагрузочные характеристики и мониторинг у них похожи, но вот по части гибкого формирования пайплайна у Airflow дела обстоя чуточку лучше -- можно написать относительно простой код на питоне для пайплайна. В то время как для SCDF придется писать больше кода на Java. Т.е. разработка на SCDF будет вестись дольше. 
Также у Airflow гораздо лучше и проще интеграция с облачными провайдерами и внешними
сервисами типа бд, шинами данных и т.п. Никаких проблем при использовании Airflow в облаке
возникнуть не должно. SCDF дела с интеграцией хуже, нужно приложить больше усилий для разворачивания и запуска соотв. инф-ры. По части интеграции с внешними сервисами дела
обстоят чуть хуже чем у Airflow и придется писать код (обертки) на Java.

Вывод: кажется, что решение на Airflow можно сделать гораздо быстрее, т.к. понятная модель
программирования(описание DAG на питон) и есть многое "из коробки" для работы с внешними сервисами. К тому же Airflow гораздо лучше интегрирован в облака. Таким образом, в качестве решения для пакетной обработки данных предлагается Airflow.
